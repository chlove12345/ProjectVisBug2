# VisBug2 开发代理工作约定

> 适用范围：本仓库的后续开发任务。先遵守用户当前指令，再遵守仓库内现有约定。本文件是放在 `docx/` 的交付文档；若要让依赖 `AGENTS.md` 文件名的工具自动读取，需要另行在仓库根目录配置，不能假定本文件会被自动加载。

## 1. 开始任务

1. 先读任务要求、`git status --short --branch`、相关源码、`.editorconfig`、`CONTRIBUTE.md` 和 `docx/development-standards.md`。不要覆盖已有的未提交改动。
2. 确认当前分支和任务边界。此仓库是 fork；开发使用独立分支。当前文档任务在 `dev` 分支，**不得自动合并到 `main`，也不得未经用户要求推送或创建发布**。
3. 对需求中有歧义但可以继续的部分，写明采用的假设并推进；只有关键输入缺失时才提问。
4. 描述已有行为时给出文件或测试依据。将“代码中观察到的现状”和“建议的新规范”区分开。

## 2. 修改原则

- 只改为完成任务所需的文件与代码。使用小范围补丁，修改前后检查差异；保留同一文件内用户和他人的无关改动。
- 优先沿用项目的原生 ES modules、自定义元素、Shadow DOM、功能模块和现有工具链，不为局部需求引入新框架或依赖。
- 新功能放在相应的 `app/features/`、`app/components/` 或 `app/plugins/`。功能启用时注册的监听器、快捷键、观察器、动画帧及临时 DOM，停用时应清理。
- 会改变页面的操作应考虑 `HistoryManager`：样式优先用 `recordStyleChanges`，DOM、属性和文字变化使用对应的 `Change` 类型；检查撤销和重做后的覆盖层状态。
- 页面内容视为不可信输入。谨慎使用 `innerHTML`、剪贴板内容、动态选择器和外部资源；不要把用户页面的数据或密钥写进日志、测试夹具或文档。
- 扩展相关改动同时核对 `extension/manifest.json`、注入流程、构建复制脚本以及目标浏览器差异。生成的 bundle 和 `artifacts/` 不作为手写源码提交。

## 3. 验证与报告

- 按变更范围运行相关检查。普通前端改动至少执行 `npm run bundle` 和相关测试；扩展资源或打包流程改动执行 `npm run extension:build`；涉及浏览器交互时运行相应的 AVA/Puppeteer 测试，必要时执行 `npm run test:ci`。
- 测试失败要定位是代码问题、环境问题还是既有失败；不能把“未运行”“模拟通过”或“尚待批准”写成“已验证通过”。
- 完成前检查 `git diff --check`、`git diff --stat` 和实际差异，确认没有意外的整文件重写、无关改动、生成物或敏感信息。
- 汇报应包含：做了什么、为什么、实际运行了哪些检查及结果、未验证的部分、当前分支。不要声称已合并或已发布，除非有对应操作证据。

## 4. 这些规则要避免的常见问题

公开反馈中常见的痛点包括：结果“差一点就对”但仍需人工修正、调试 AI 代码耗时、忽略仓库指令、局部任务改动过大、把未执行的验证写成已完成。对应措施是先读约定、限定改动范围、运行有意义的检查、复核差异，并如实报告证据。来源和适用边界见 `docx/development-standards.md` 的“外部反馈与规则映射”。
